# D20bench Tactical Tournament Plan

## North Star

Build a reproducible tactical combat benchmark where LLMs control D&D-style characters and monsters under a strict action schema. The system should answer: "Which model, prompt, and tactical policy wins more often under the same Battlecast-compatible SRD rules, maps, teams, and random seeds?"

## Core Product

The first usable version should support:

- Two-sided grid combat with deterministic initiative, movement, attacks, saves, reactions, conditions, hit points, and simple objectives.
- SRD rules behavior matching Battlecast's implementation wherever Battlecast has already encoded the rule.
- LLM agents that receive a concise combat observation and must return a validated JSON action.
- Scripted baseline agents for non-LLM comparison.
- Seeded match execution, full replay logs, state hashes, and model/prompt metadata.
- A CLI runner for local tournaments and a generated leaderboard report.
- A public results website that presents benchmark suites, Elo-style head-to-head battles, model pages, and replay links.

## Current Product Decisions

- **Rules scope**: SRD rules as implemented in Battlecast, copied or adapted into this repo.
- **Public identity**: D20bench.
- **Website stack**: Battlecast ecosystem: TypeScript, React, Vite, Vitest, Playwright where useful.
- **Benchmark philosophy**: visible public scenarios, hidden eval suites, and private Elo arena seasons whose archived results can be published without exposing hidden details.
- **Initial model strategy**: start with strong agentic models such as Kimi K2, Claude Sonnet, and DeepSeek before spending on frontier model sweeps.
- **Initial budget posture**: target roughly $50 for early OpenRouter experiments, with per-run caps and cost reporting before larger seasons.
- **Battlecast reuse**: Battlecast may be freely reused by D20bench, but the sibling repo stays read-only and all copied/imported material should carry provenance.

## Tournament Formats

- **Duel**: one creature or character per side. Fast sanity tests for legality, targeting, and core tactical competence.
- **Squad skirmish**: small symmetric teams, such as 3v3 or 4v4, where focus fire, positioning, and support actions matter.
- **Encounter challenge**: a fixed party faces a monster group. Useful for measuring encounter-solving behavior.
- **Monster mirror**: same stat blocks on both sides. Best for isolating the agent from team composition bias.
- **Draft or loadout cup**: agents pick from constrained rosters before combat. Later phase, once in-combat evals are stable.
- **Scenario puzzles**: hand-authored tactical states with known strong lines, such as escaping melee, finishing a low-HP target, or avoiding an area effect.

## Agent Contract

Agents should never free-form mutate game state. They receive an observation and choose from legal action primitives.

Observation fields:

- Match id, seed, round, turn, active unit, initiative order.
- Public map state: grid, terrain, cover, hazards, objectives.
- Visible units: position, allegiance, HP band or exact HP depending on benchmark mode, AC if known, conditions, concentration, available reactions.
- Active unit resources: speed remaining, action economy, spell slots or limited-use abilities, legal targets.
- Legal action catalogue generated by the engine for the current unit.

Action response:

```json
{
  "intent": "focus the wounded enemy before it can act",
  "actions": [
    {
      "type": "move",
      "path": [[4, 3], [5, 3]]
    },
    {
      "type": "attack",
      "action_id": "shortbow",
      "target_id": "goblin_2"
    }
  ]
}
```

Validation policy:

- Invalid JSON: retry with a repair prompt once, then forfeit the turn.
- Illegal action: reject, explain the legality error to the agent, retry once, then use `dodge` or `end_turn`.
- Ambiguous target or path: reject rather than guess.
- Model timeout: forfeit the turn.

## Tactical Baselines

Baseline agents make the benchmark useful before LLMs enter the loop.

- **Random legal**: samples any legal action. Establishes a floor.
- **Nearest target**: moves toward and attacks the closest enemy.
- **Focus fire**: targets the enemy with the lowest effective HP among reachable targets.
- **Expected damage**: chooses the legal attack or spell with the highest immediate expected damage.
- **Kiter**: maintains range, uses ranged attacks, avoids opportunity attacks where possible.
- **Tank screen**: blocks paths to fragile allies and prioritizes opportunity-control positions.
- **Nova striker**: spends limited resources early to remove enemies.
- **Conservative caster**: values concentration, range, cover, and spell-slot preservation.
- **Objective first**: optimizes map objectives over kills.
- **Battlecast tactics**: imported or reimplemented tactics from Battlecast where licensing allows.

## Benchmark Suites

- **Legality suite**: short scenarios designed to catch illegal movement, invalid targets, action economy mistakes, concentration errors, and reaction misuse.
- **Micro tactics suite**: tactical puzzles with one to three turns of expected strong play.
- **Skirmish suite**: balanced mirrored fights across maps and seeds.
- **Encounter suite**: party-vs-monster scenarios at different difficulty bands.
- **Robustness suite**: same game state rendered with harmless wording changes to test prompt sensitivity.
- **Cost and latency suite**: tracks tokens, wall-clock latency, retry count, and failed turns.

## Metrics

Primary:

- Win rate by scenario family.
- Elo or Glicko rating by agent version.
- Illegal action rate.
- Timeout and repair rate.

Secondary:

- Damage dealt and taken per round.
- Objective score.
- Survival turns.
- Resource efficiency.
- Focus-fire consistency.
- Positioning features such as cover use, distance maintained, and avoidable opportunity attacks.
- Tactical regret versus shallow search or scripted oracle in small scenarios.

## Ladder Design

Use a season-based ladder so ratings stay interpretable as rules and prompts evolve.

- Rating identity: `model + provider + parameters + system prompt + agent code version + ruleset version`.
- Start with Elo for two-sided matches; move to Glicko-2 for uncertainty or TrueSkill if multi-agent team formats become central.
- Pairings should be stratified by scenario family so one model does not farm a narrow encounter type.
- Publish separate boards for legality, duel, skirmish, encounter, and cost-adjusted performance.
- Store all seeds, prompts, observations, responses, dice rolls, and final state hashes for auditability.

## Public Results Website

The website should be the public face of the benchmark, inspired by LMArena's model leaderboard and matchup exploration. It should consume generated season artifacts rather than compute results itself.

- Overall leaderboard with Elo/Glicko rating, confidence, win rate, illegal action rate, cost, latency, and benchmark version.
- Head-to-head pages for model-vs-model records, scenario-family breakdowns, and representative battles.
- Model pages showing rating history, prompt/config identity, provider metadata, strengths, weaknesses, and notable replays.
- Season pages that freeze the scenario pool, ruleset, data pack, seeds, agent roster, and rating parameters.
- Replay pages that let users inspect turn-by-turn actions, accepted/rejected moves, dice rolls, state hashes, and prompt/response artifacts where public.
- Static JSON outputs for charts and reproducibility, so the published site can be regenerated from audited benchmark artifacts.

## Architecture

```text
D20bench
  engine/
    state model, turn runner, action validator, dice, line of sight
  data/
    canonical monster/action/spell/map/scenario schemas
  adapters/
    battlecast importers and compatibility layer
  agents/
    baseline policies and LLM provider adapters
  evals/
    scenario suites, match runner, tournament scheduler
  ratings/
    Elo/Glicko calculations and season snapshots
  replays/
    JSONL match logs and optional graphical renderer
  ui/
    public benchmark website, leaderboard, matchup pages, and replay viewer
```

## MVP Milestones

1. **Repo and source audit**
   - Keep Battlecast as a read-only sibling checkout.
   - Inspect license, data provenance, monster schemas, engine boundaries, and graphical asset ownership.

2. **Rules-core spike**
   - Implement or adapt deterministic turn execution.
   - Support movement, attacks, damage, death saves if needed, conditions, and simple spell-like abilities.
   - Add state-hash snapshots for replay verification.

3. **Scenario and baseline layer**
   - Define canonical scenario schema.
   - Add random, nearest-target, focus-fire, and expected-damage agents.
   - Run batch matches locally with seeded output.

4. **LLM agent harness**
   - Add provider adapters, prompt templates, JSON schema validation, retry policy, and token/cost logging.
   - Start with one active unit per LLM turn.

5. **Benchmark reports**
   - Generate static markdown/HTML reports with win rates, legality rates, cost, latency, and replay links.
   - Add CI smoke evals using scripted agents.

6. **Rating ladder**
   - Add season configs, match scheduling, Elo/Glicko updates, and leaderboard publishing.

7. **Replay and graphics**
   - Publish a public benchmark website from generated season artifacts.
   - Add LMArena-style leaderboard, head-to-head matchup pages, model pages, and season pages.
   - Reuse Battlecast graphical representations where permitted.
   - Build a deterministic replay viewer from match logs.

## Key Risks

- **Licensing and attribution**: D&D data can be legally subtle. We should separate SRD/CC/OGL-compatible data from any product-identity material and document every source.
- **Rules complexity**: Full D&D combat is large. The benchmark should start with a strict tactical subset and expand behind versioned rulesets.
- **LLM nondeterminism**: Store every prompt, response, model id, parameters, seed, and retry to make results auditable.
- **Prompt leakage**: Scenario descriptions and creature names should be treated as untrusted strings in prompts.
- **Overfitting**: Keep public practice scenarios separate from private or rotating ladder scenarios.
